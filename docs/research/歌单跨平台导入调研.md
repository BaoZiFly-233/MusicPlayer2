# 歌单跨平台导入调研

调研时间：2026-09-13。所有接口结论都是本机真实 HTTP 请求实测的结果（PowerShell + Invoke-WebRequest）。

## 结论

**可行，工作量主要在「匹配算法」而不是「拿数据」。**

- 网易云最容易：2 个免登录免签名接口就能拿全歌单
- QQ 音乐次之：只需要正确的 `Referer`
- **没有任何开源项目做过「网易云/QQ → 酷狗/酷我」这个组合**，需要自己写
- 匹配算法本身不难（Levenshtein + 加权），但有 5 个实测出来的坑，踩了就静默导错歌

本项目已有「导入自己平台歌单」的能力（`Action::OpenPlaylist` / `Action::ImportAll`），缺的只是「其他平台作为来源」。目标侧（`IOnlineSource::Search()`）已经就绪，拿来即用。

## 各平台导出歌单能力

| 平台 | 难度 | 登录/签名 |
|---|---|---|
| 网易云 | 最容易 | 都不需要 |
| QQ 音乐 | 中 | 只需要 `Referer: https://y.qq.com/` |
| 酷我 | 中 | 不需要（老接口还活着，Web 接口已废） |
| 酷狗 | 中 | 不需要，但**必须走 HTTP**（HTTPS 握手失败） |
| Spotify | 很难 | 必须 OAuth，实测 401；本机也连不上 open.spotify.com |

### 网易云（推荐首选）

```
1) GET https://music.163.com/api/v6/playlist/detail?id=<歌单id>&n=1000
   → playlist.name / trackCount / trackIds[].id
2) GET https://api/song/detail?ids=[id1,id2,...]
   → 补齐元数据，一次最多 200 个 id
```

免登录、免签名、免 Cookie。

**最大的坑：`&n=` 参数只对官方排行榜有效，普通用户歌单无论传多大都只给 10 首。**

实测（`trackCount=50` 的用户歌单）：

```
n=1    → tracks=1    trackIds=50
n=10   → tracks=10   trackIds=50
n=50   → tracks=10   trackIds=50     ← 卡在 10
n=1000 → tracks=10   trackIds=50
```

官方榜单 `3778678`（`trackCount=200`）传 `n=1000` 能到 200。所以这是**普通歌单的固定上限**，跟版权/灰色无关。

⚠️ 代码里**不要**写成「过滤掉不可播放的」那种防御逻辑 —— 真正的问题是**必须忽略 `tracks` 字段**，只信 `trackIds`，再用 `song/detail` 补全。否则用户会发现导入的歌单比原歌单短。

`song/detail` 批量建议每批 **100** 个 id（测过 200 正常、500 只回 201，100 稳妥且 URL 长度可控）。

字段：`songs[].name` / `artists[].name` / `album.name` / `duration`（毫秒）。

实测耗时：200 首歌单 → 2 次请求约 1.1 秒。

### QQ 音乐（并列首选 —— 实际上比网易云更省事）

两个接口都免登录，**唯一门槛是 Referer**（不对会返回 `invalid referer`）。

**实测：一次请求拿到全量。** `disstid=9123641054` → `songnum=2530`，`songlist` 也是 2530 条，不用分页、不用第二步补全。所以 QQ 比网易云（两步走）更省事。

推荐用这个地址（实测校准过，必需的是 Referer）：

```
GET https://i.y.qq.com/qzone-music/fcg-bin/fcg_ucc_getcdinfo_byids_cp.fcg
    ?type=1&json=1&utf8=1&onlysong=0&nosign=1&disstid=<id>
    &g_tk=5381&loginUin=0&hostUin=0&format=json
    &inCharset=GB2312&outCharset=utf-8&notice=0&platform=yqq&needNewCode=0
Header: Referer: https://y.qq.com/   （建议同时带浏览器 UA）
```

注意：「我喜欢」这类个人收藏需要登录（实测 `songnum=0`）。

```
GET https://c.y.qq.com/qzone/fcg-bin/fcg_ucc_getcdinfo_byids_cp.fcg
    ?type=1&json=1&utf8=1&onlysong=0&disstid=<id>&format=json
    Header: Referer: https://y.qq.com/
→ cdlist[0].songlist[]: songname / singer[].name / albumname / interval(秒) / songmid
```

支持分页的新接口：

```
GET https://u.y.qq.com/cgi-bin/musicu.fcg?data=<URL编码的JSON>
  {"comm":{"ct":24,"cv":0},"req_1":{"module":"music.srfDissInfo.aiDissInfo",
   "method":"uniform_get_Dissinfo","param":{"disstid":<id>,"song_begin":0,"song_num":100}}}
→ req_1.data.songlist[]: title / singer[].name / album.name / interval(秒) / mid
  req_1.data.dirinfo.songnum = 总数
```

### 酷我

```
GET http://nplserver.kuwo.cn/pl.svc?op=getlistinfo&pid=<歌单id>&pn=0&rn=1000
    &encode=utf-8&keyset=pl2012&identity=kuwo&vipver=MUSIC_9.1.1.2_BCS2&newver=1
→ {result:"ok", title, uname, total, musiclist:[{name, artist, album, duration(秒)}]}
```

`https://www.kuwo.cn/api/www/playlist/playListInfo` 等 Web 接口**已加反爬**，无论怎么带 Cookie/csrf 都返回 `The request is illegal!`，别浪费时间。

### 酷狗

```
GET http://mobilecdn.kugou.com/api/v3/special/song
    ?plat=0&specialid=<id>&page=1&pagesize=100&version=8352&with_res_tag=1
```

必须用 HTTP。响应被 `<!--KG_TAG_RES_START-->` 包裹，解析前要剥掉。

字段：`data.info[]` 有 `hash`、`filename`（形如 `"笑天 - 别再让我等太久 (DJ何鹏版)"`）、`duration`（秒）。**没有独立的歌手字段**，要从 `filename` 里按 `" - "` 切。

对本项目意义不大 —— 酷狗自己的歌单已经能导了。

## 分享链接格式与提取规则

各平台规范链接（都实测过 200）：

```
网易云   https://music.163.com/playlist?id=3778678
QQ      https://y.qq.com/n/ryqq/playlist/7011264340
        https://i.y.qq.com/n2/m/share/details/taoge.html?id=7011264340
酷狗     https://www.kugou.com/yy/special/single/6130000.html
        https://www.kugou.com/songlist/gcid_3zb1c0b1z3z0a1/    （新版是 gcid_ 前缀）
酷我     https://www.kuwo.cn/playlist_detail/3720681210
Spotify https://open.spotify.com/playlist/37i9dQZF1DXcBWIGoYBM5M
```

提取规则：网易云/QQ 取 `id=` 或路径里的数字；酷狗取 `single/(\d+)` 或 `(gcid_[a-z0-9]+)`；酷我取 `playlist_detail/(\d+)`。短链（`163cn.tv/xxx`）返回 302，跟随重定向即可。

**更省事的做法：不区分平台。** 把用户粘贴的整段文本丢给一组正则，哪个先命中就用哪个解析器，同时把文本里所有数字 ID 也作为候选。用户从 App 复制的分享文本形如「分享歌单 《xxx》 http://163cn.tv/xxxxx 来自@网易云音乐」，正则可直接捞出链接。

## 匹配算法

### 目标侧已有能力

- 酷狗：`CKugouSource::Search()`（带签名）
- 波点：`CBodianSource::Search()`（匿名）

### 五个实测出来的坑

**坑 1：版本词黑名单必须作用在「未去括号」的归一化串上。**
若先把 `(...)` 剥掉再查黑名单，`Lip & Hip (Live)` 会变成 `lip hip`，`live` 永远查不到，黑名单形同虚设。正确做法：比对歌名时用「去括号」版本（这样 `泫雅 (HyunA)` 能和 `泫雅` 匹配），但查黑名单时用原始归一化串。

**坑 2：只扣分不够，必须改排序。**
`Lip & Hip (Live)` 歌名满分、歌手满分、时长只差 0.7 秒 → base 98.7，扣 15 分还有 83.7，会被「自动采用」。正确做法是**双键排序：先按版本词命中数升序，再按分数降序**，惩罚加到 -20。

**坑 3：歌手名要拆开两两比较取最大值，不能整串比。**
网易云给 `泫雅/郑镒勋`，波点给 `泫雅 (HyunA)&정일훈` —— 同一个人，中文名 vs 韩文名。整串比会掉到 50 分以下，误杀正确结果。拆成单个歌手后两两取 max 后，波点匹配率从 5/8 回到 8/8。

**坑 4：波点的 `duration` 有时是 60 秒试听片段。**
时长硬规则（差 >30 秒否决）正好能筛掉片段、留下完整版。但**前提是不能因为「候选时长缺失」就否决** —— 正确做法是字段缺失时不计入加权分母，而不是按 0 分算。这条比权重数值本身更重要。

**坑 5：波点歌手名普遍带别名括号。**
`泫雅 (HyunA)`、`马也_Crabbit&Fanko`。去括号 + 拆分后两个坑一起解决。

### 实测匹配率

- **波点：8/8 自动采用，平均 100.0 分**
- 酷狗：3 自动 / 2 待确认 / 3 未找到（但用的是免签名 web 搜索接口，返回的多是翻唱和现场版，是数据源问题。**应该用项目自己的签名搜索接口重测**）

测试歌单是 K-pop（难例），华语流行会更容易。

### 推荐算法

```
相似度内核：Levenshtein 归一化 (1 - lev/max(len)) * 100
歌名：max(整串词级相似度, 去括号后词级相似度)
歌手：拆成单个歌手后两两取 max
时长：3 秒内免罚，30 秒归零，线性衰减
权重：歌名 3.0 / 歌手 2.0 / 时长 2.0（只把双方都有值的字段计入分母）
版本词命中：-20 分/个，且作为第一排序键
硬淘汰：歌名 <60、歌手 <70、时长差 >30 秒
分档：≥80 自动采用 / 65~80 待确认 / <65 未找到
```

版本词黑名单（中英都要）：

```
live / remix / remaster / cover / acoustic / instrumental / karaoke /
concert / slowed / version / 现场 / 片段 / 翻唱 / 伴奏 / 演唱会 / 铃声 /
音乐银行 / 人气歌谣 / dj版
```

**源歌名本身就含该词时不扣**（否则《Live Forever》会被误杀）。

每首歌正常 1 次搜索请求：`第一位歌手 - 歌名`（歌手名超 15 字符截断），一次拿 20~50 条候选在本地全部打分。只有最佳分 <65 时才换关键词再搜，最多 3 次。

## 成本估算（实测）

- 网易云 200 首 = 2 次请求，约 1.1 秒
- 目标搜索：波点约 510ms/次，酷狗约 250ms/次
- 100 首 × 2 平台串行约 100 秒；开 3~4 个并发线程约 30 秒

## 可借鉴与不要碰的项目

| 项目 | 许可 | 能借鉴什么 |
|---|---|---|
| [spotDL/spotify-downloader](https://github.com/spotdl/spotify-downloader) | MIT | 唯一把打分公式、阈值、版本词黑名单做全的 |
| [beets](https://github.com/beetbox/beets) | MIT | 加权距离模型、括号降权 |
| [listen1](https://github.com/listen1/listen1_chrome_extension) | MIT | 各平台 provider 与歌单解析 |

**不要抄的**：

- `DJChanahCJD/otter-music` —— **没有 LICENSE 文件**，只能看思路
- `metabrainz/picard` —— GPL-2.0，有传染性，只参考思路
- `UnblockNeteaseMusic/server` —— 匹配只有「时长 5 秒容差 + 兜底取第一条」，不算歌名相似度，短板明显

**被高估的**：

- `yueyericardo/Netease-to-Youtube-or-Spotify`（755★）**根本没有匹配算法**，只是把「歌名 - 歌手」拼成文本让用户自己复制
- `akasa828/Netease2QQ` 是空壳仓库，只有 LICENSE，没有一行代码
- 谷登 GD Studio API 实测不可靠：`source=kuwo` 返回的却是网易云格式的另一个歌单

**没有找到**：C++ 的歌曲元数据匹配库；「歌曲匹配」类的通用开源库（搜到的全是声纹指纹方向）。

## 给本项目的实现建议

1. 第一版只做**网易云 + QQ 音乐**两个来源，性价比最高
2. **不要做 Spotify**（要 OAuth + 注册开发者应用，收益远低于成本）
3. 主路径走「粘贴分享链接/文本」+ 正则提取编号；**纯文本解析作为兜底入口**（网上很多工具导出的就是逐行「歌名 - 歌手」，且共用同一套匹配代码）
4. 新增 `CPlaylistImporter`（各平台解析成统一的 `vector<ImportTrack>{title, artist, album, duration_ms}`）+ `CSongMatcher`（纯函数，好测），复用现有 `IOnlineSource::Search()` 拿候选
5. **必须加并发 + 进度 + 取消**。现有浏览是单线程串行，100 首要跑 1~2 分钟，用户会以为卡死
6. 匹配结果分三档展示：自动采用的直接进歌单，「待确认」和「未找到」给用户列表手动处理
